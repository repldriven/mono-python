# Server gap analysis

Report-only gap analysis of the server brick against [server](../server.md),
the design it implements, both read at the commit named above on `main`.
Gas City workflow root `mopy-115`, bead `mopy-xvn`. No bead, branch or
source file was changed; the commands under Evidence were run and their
output recorded.

## Verdict

**fail.** The design's Objective puts the whole brick in scope — the
three components, the app assembly, the error bodies, the health routes,
the idempotency key, CORS, the OpenAPI page, registration in both
`pyproject.toml` files and the readme, and the tests — and the build
stops at the first of the four slices "The first slice" lists. A
consumer pinning a tag receives no server brick.

The first slice passes. Every operation and file the Status banner says
exists does, every claim in the Tests section for `test_system.py` and
`test_adapter.py` has a test, and the tests and checks are green. The
banner and Known Limitations record the gaps, with the exceptions under
Findings.

## Evidence

Run at the commit above, through the flake, on Python 3.14.7 with
litestar 2.24.0, uvicorn 0.53.0 and msgspec 0.21.1 installed:

- `just test components/server`: 18 passed.
- `just test -m "not docker"`: 52 passed, 7 deselected.
- `just check`: format, lint and `poly check` all pass.
- `just poly info`: `server` is in `development` and not in
  `mono-bricks`.
- `server.__all__` exports `AppCtx`, `app`, `default_exception_handlers`,
  `http_local_url` and `problem`; `health_routes` and
  `require_idempotency_key` are absent.
- `server.app` over an `AppCtx` whose `cors` names an origin returns a
  `Litestar` whose `cors_config` is `None`, whose OpenAPI render plugins
  are Litestar's defaults with no Scalar plugin, and whose routes are
  the handler given, `/schema` and its children, and no `/actuator`
  path.
- `msgspec` is a dependency of `litestar` and is declared in neither
  `pyproject.toml`.
- `.github/` holds no workflow.

## Findings

Ordered by severity. Each names the section of the design it is
measured against.

- **Slices 2 to 4 are not built.** Against "The first slice", "Health
  routes", "The idempotency key", "CORS", "The app assembly" and
  "Registration and release": `health_routes`,
  `require_idempotency_key`, the `CORSConfig` from `AppCtx.cors`, the
  brick's `OpenAPIConfig` with `ScalarRenderPlugin`,
  `test_interface.py`, the entry in `projects/bricks/pyproject.toml`,
  the readme row and the tag do not exist. The banner lists each.
- **The brick does not ship.** Against "Registration and release":
  `projects/bricks/pyproject.toml` names neither the brick nor
  `litestar` and `uvicorn`, so the wheel a consumer pins carries no
  `mono_bricks.server` and its environment has no Litestar to run one.
  Known Limitations records it. It is the one gap a consumer meets.
- **`ready_fn` is accepted and ignored.** Against "The uvicorn adapter
  component" and "Health routes": `_start_adapter` in
  [system.py](/components/server/src/mono_bricks/server/system.py)
  coerces the key — `None` to always ready, a `threading.Event` to its
  `is_set` — into `AppCtx.ready_fn`, and `app` adds no health routes,
  so nothing reads it. A base that passes an `Event` at start observes
  nothing, as a `cors` block permits nothing. Known Limitations records
  `cors` and not `ready_fn`, and the YAML under "A system" carries a
  `cors` block without saying it does nothing yet.
- **`msgspec` is imported and not declared.** Against "The library",
  which names `litestar` and `uvicorn` as the brick's libraries in both
  `pyproject.toml` files:
  [core.py](/components/server/src/mono_bricks/server/core.py) imports
  `msgspec` to tell a body that failed to decode from a return value
  that failed to encode. The import resolves through Litestar's own
  dependency, which a Litestar upgrade may change, and the design does
  not name it.
- **The CORS section describes the preflight as middleware.** Against
  "CORS": Litestar answers a preflight through an `OPTIONS` handler it
  generates for each route, with status 204 and
  `CORSConfig.preflight_headers`, not through middleware before
  routing; a preflight on a path no route claims is a 404. The outcome
  the design wants — a route with no `OPTIONS` handler of its own
  answers its preflight — holds, and the sentence giving the mechanism
  does not. `CORSConfig` defaults `allow_methods` and `allow_headers`
  to `*` and `max_age` to 600 where mono's `cors.clj` lists the
  methods and headers and uses 3600, so the second slice sets mono's
  defaults rather than inheriting the library's. `Vary: Origin` it
  sets, as mono did.
- **The handler example disagrees with the code.** Against "The
  dependencies component": the example annotates `store: Store` where
  the docstring and tests use `NamedDependency[Store]`. Known
  Limitations records it, and the example is unchanged.

## First slice against the design

The banner's list of what exists is accurate: the three kinds in
`system.py`; `AppCtx`, `app`, `problem` and `default_exception_handlers`
in `core.py`; and `bind`, `RequestLog`, `serve`, `shutdown` and
`http_local_url` in
[adapter.py](/components/server/src/mono_bricks/server/adapter.py).
The adapter's config keys and defaults, the exclusive bind on port 0,
the start timeout and the `StartError` it becomes, the two logging
arguments, the request log's shape and the `Listening on` line each
match their section. Every claim in the Tests section for
`test_system.py` and `test_adapter.py` has a test in
[test_system.py](/components/server/test/mono_bricks/server/test_system.py)
and
[test_adapter.py](/components/server/test/mono_bricks/server/test_adapter.py),
and two tests go beyond it: an `app` that raises, and one whose startup
hook fails, each failing start with a `StartError` naming the adapter.

## Missing evidence

- **No run outside one machine.** `.github/` holds no workflow, so the
  fourth slice's "`just test` and `just check` green" has this
  report's local runs as its only record.
- **The `ready_fn` branches.** Neither the `None` nor the
  `threading.Event` branch of `_start_adapter` has a test, and until
  the health routes exist neither has an observable effect to test.
- **The fallback client error.** `_client_error` answers a
  `ClientException` that is not a decode failure — a handler raising
  Litestar's 401 or 403 — as a problem body with Litestar's title and
  no mono `type`; no test exercises it, and "The error bodies" does not
  list the case.
- **A stop that times out.** `shutdown` raises when the thread outlives
  its timeout; no test reaches it.

## Recommended fixes

In the order the design's slices give:

1. Build the second slice: `health_routes(ready_fn)` on mono's three
   paths, added by `app` from `ctx.ready_fn`; `require_idempotency_key`
   with mono's regex and its two `detail` strings; `CORSConfig` from
   `AppCtx.cors`, setting `allow_methods`, `allow_headers` and
   `max_age` to `cors.clj`'s defaults when the block leaves them out;
   and `test_interface.py` proving each, the preflight test on a path a
   route claims.
2. Build the third slice: the brick's `OpenAPIConfig` with
   `ScalarRenderPlugin` as `app`'s default when the caller passes none,
   and its test.
3. Ship: add the brick, `litestar` and `uvicorn` to
   `projects/bricks/pyproject.toml` and the row to the readme, and cut
   the tag once `just poly info` shows `server` under `mono-bricks`.
4. Declare `msgspec` beside `litestar` in both `pyproject.toml` files
   and name it in "The library".
5. Edit the design: annotate the example under "The dependencies
   component" `NamedDependency[Store]`; add `ready_fn` to the `cors`
   entry in Known Limitations, or delete both once the second slice
   lands; say under "CORS" that Litestar answers a preflight through
   the `OPTIONS` handler it generates per route.
6. Add a test for the fallback client error and list the case under
   "The error bodies", or route it through `problem` with a mono
   `type`.
7. A workflow running `just test -m "not docker"` and `just check` on
   push would record the fourth slice's green outside one machine.
